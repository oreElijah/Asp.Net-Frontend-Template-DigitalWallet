Build a frontend UI for the DigitalWallet ASP.NET backend. The backend is exposed at /api/v1.0 and supports Students, Merchants, Admins, SchoolAdmins, Wallet operations, and Transaction operations. The frontend must match the backend API contracts, request/response DTOs, role-based routes, and data relationships.

---

## 1. Overview

- Backend base path: /api/v1.0
- Role-based access:
  - Student
  - Merchant
  - Admin
  - SchoolAdmin
- Authentication is cookie-based:
  - ACCESS_TOKEN
  - REFRESH_TOKEN
- Add UI pages for login, registration, dashboard, profile, transaction flows, wallet search, school management, merchant approval, and admin management.
- Use API-friendly JSON plus multipart/form-data where required.
- The frontend must support:
  - login / logout
  - registration with uploads
  - profile view/update
  - transaction history
  - deposit, withdrawal, transfer, scan-to-charge
  - wallet search and wallet transaction details
  - school creation, update, delete, lookup
  - admin/schooladmin controls

---

## 2. API route conventions

The backend is versioned with v{version:apiVersion} and controller names form routes:

- AccountController → /api/v1.0/Account/
- StudentController → /api/v1.0/Student/
- MerchantController → /api/v1.0/Merchant/
- TransactionController → /api/v1.0/Transaction/
- WalletController → /api/v1.0/Wallet/
- SchoolController → /api/v1.0/School/
- AdminController → /api/v1.0/Admin/
- SchoolAdminController → /api/v1.0/SchoolAdmin/

Routes are defined using ASP.NET Core attributes like [HttpGet], [HttpPost], [HttpPut], [HttpDelete].

## 3. Authentication and account routes

### 3.1 Login
- POST /api/v1.0/Account/login
- Request body:
  - WalletNumber
  - Password
- Response:
  - UserId
  - ProfilePicture
  - Firstname
  - Lastname
  - SchoolCode
  - Email
  - WalletNumber
  - Token
- Notes:
  - This is the primary login route for standard users.
  - The backend checks email confirmation and merchant approval.
  - Success sets cookies ACCESS_TOKEN and REFRESH_TOKEN.

### 3.2 Logout
- POST /api/v1.0/Account/logout
- No request body
- Requires authorization
- Clears authentication state server-side

### 3.3 Change password
- POST /api/v1.0/Account/change_password
- Request body:
  - CurrentPassword
  - NewPassword
- Requires authorization
- Only authenticated users can call this

### 3.4 Forgot password
- POST /api/v1.0/Account/forgot_password
- Request body:
  - Email
- Sends password reset email
- Response returns email and token in plain response text

### 3.5 Reset password
- POST /api/v1.0/Account/reset_password?email={email}&token={token}
- Request body:
  - Password
- Email and reset token are passed in query parameters
- The body contains new password

### 3.6 Email verification
- GET /api/v1.0/Account/verify_email?email={email}&token={token}
- Verifies registration email
- Query string contains both email and token
- Returns success or failure message

### 3.7 Google login flow
- GET /api/v1.0/Account/login/google
- GET /api/v1.0/Account/login/google/callback
- OAuth redirect-based login
- Not primary for frontend if using standard credentials
- Should still support if external login is desired

## 4. Student API routes

### 4.1 Student registration
- POST /api/v1.0/Student/register
- Requires multipart/form-data for file upload
- Fields:
  - Firstname
  - Lastname
  - ProfilePicture (optional file)
  - MatricNumber
  - SchoolCode
  - Pin
  - Password
- Response:
  - UserId
  - ProfilePicture
  - Firstname
  - Lastname
  - MatricNumber
  - SchoolCode
  - Email
  - WalletNumber
  - Message
- Validation rules:
  - Firstname required
  - Lastname required
  - MatricNumber required
  - SchoolCode required
  - Pin required, exactly 4 digits
  - Password required
  - Email required and must be valid

### 4.2 Get student profile
- GET /api/v1.0/Student/profile
- Requires authorization, student role
- Response:
  - UserId
  - ProfilePicture
  - Firstname
  - Lastname
  - MatricNumber
  - SchoolCode
  - SchoolName
  - Email
  - WalletNumber

### 4.3 Update student profile
- PUT /api/v1.0/Student/update_profile
- Requires authorization, student role
- Multipart/form-data optional file
- Fields:
  - Firstname
  - Lastname
  - ProfilePicture
- Response:
  - Updated UserProfileResponseDto fields

## 6. Transaction API routes

### 6.1 Transaction history
- GET /api/v1.0/Transaction/history
- Requires authorization
- Returns AppResponse with transaction list

### 6.2 Deposit
- POST /api/v1.0/Transaction/Deposit
- Requires authorization, Student role
- Request body:
  - Amount
- Response:
  - AppResponse<DepositResponseDto>
  - DepositResponseDto contains nested TransactionDto

### 6.3 Withdrawal
- POST /api/v1.0/Transaction/Withdrawal
- Requires authorization, Merchant role
- Request body:
  - Amount
  - Pin
- Response:
  - AppResponse<TransactionDto>

### 6.4 Transfer
- POST /api/v1.0/Transaction/Transfer
- Requires authorization, Student role
- Request body:
  - ReceiverWalletNumber
  - Amount
  - Description
  - Pin
- Response:
  - AppResponse<TransactionDto>

### 6.5 Scan to charge
- POST /api/v1.0/Transaction/scan_to_charge
- Requires authorization, Merchant role
- Request content type: multipart/form-data
- Fields:
  - BarcodeScanDto fields
  - Amount
  - Pin
- Response:
  - AppResponse<TransactionDto>
- Use this for merchants charging customers via scanned wallet codes

### 6.6 Verify deposit
- GET /api/v1.0/Transaction/verify/Deposit/{reference}
- Requires authorization
- Verifies deposit transaction by reference

### 6.7 Verify withdrawal
- GET /api/v1.0/Transaction/verify/Withdrawal/{reference}
- Requires authorization
- Verifies withdrawal transaction by reference

### 6.8 Webhooks
- POST /api/v1.0/Transaction/webhook/Deposit
- POST /api/v1.0/Transaction/webhook/Withdrawal
- These are server-side endpoints to accept raw webhook payloads
- Not typically used in frontend UI, but note for integration

## 11. Data model and entity relationships

### 11.1 User and wallet relationship
- AppUser contains:
  - School
  - Merchant (optional)
  - Wallet
- Wallet is linked to a user
- WalletNumber is the unique identifier for login and transfers

### 11.2 Merchant and approval
- Merchant registration creates an AppUser with Merchant
- New merchants are not approved by default
- Approval is required before merchant login passes
- Merchant entity includes:
  - AccountName
  - AccountNumber
  - BankCode
  - BankName
  - BusinessName
  - ShopLocation
  - TransferRecipientCode
  - QRCodeString
  - IsApproved

### 11.3 School and user mapping
- School code links users to schools
- SchoolResponseDto has Users
- School creation and retrieval are used in registration flows

### 11.4 Transactions
- Transaction types:
  - Deposit
  - Withdrawal
  - Transfer
  - ScanToCharge
- Transaction status is tracked in TransactionStatus
- Transactions include sender and receiver wallet metadata
- WalletResponseDto includes transaction history grouped as sent and received

## 13. Frontend architecture and behavior

### 13.1 Authentication
- After login, save auth state in frontend store:
  - user
  - role
  - walletNumber
  - token
- Keep cookie-based auth for requests
- Use Authorization header only if backend expects token
- Prefer sending cookies automatically with fetch or Axios:
  - credentials: "include"
  - withCredentials: true

### 13.2 Routing
- Use route guards for authenticated sections
- Use role guards:
  - /student/*
  - /merchant/*
  - /admin/*
  - /schooladmin/*
- Redirect unauthorized users to login or error page
- Protect sensitive pages for the correct role

### 13.3 Forms and validation
- Student registration
- Merchant registration
- Login
- Password change
- Forgot/reset password
- Transfer form
- Withdrawal form
- Deposit form
- Wallet search form

## 17. Security and token handling

### 17.1 Cookie-based auth
- Send cookies on every request
- Use HttpOnly cookie mode for security
- Do not store token in local storage if cookies are used
- If token is returned in the response, store minimal auth state and rely on cookie

### 17.2 Protected routes
- Protect UI routes on the frontend
- Verify user role after login
- Fetch profile to confirm identity and role

### 17.3 Sensitive forms
- Pin fields should be masked or secure input
- Password fields should be type password
- Use HTTPS in production

### 17.4 Logout flow
- Call /Account/logout
- Clear frontend auth session
- Redirect to login

## 18. Integration details and assumptions

### 18.1 Multipart endpoints
- Student/register, Student/update_profile, Merchant/register, Merchant/update_merchant_profile, Transaction/scan_to_charge use multipart/form-data
- Use FormData and include files in the request

### 18.2 Role authorization
- Some endpoints have [Authorize(Roles = "Student")]
- Some endpoints have [Authorize(Roles = "Merchant")]
- Some endpoints have [Authorize(Roles = "Admin")]
- Some endpoints have [Authorize(Roles = "SchoolAdmin")]
- Most wallet and transaction endpoints are just [Authorize]

### 18.3 Payment provider integration
- Merchant registration resolves bank account details via IPaymentService
- Admin can request bank list from /Admin/banks
- Use bank list to populate merchant bank dropdowns

### 18.4 QR code generation
- Merchant controller stores QRCodeString as base64
- /Merchant/View/qrcode returns bytes
- /Merchant/qrcode downloads PNG
- Frontend should optionally render base64 image or offer a download from the endpoint

## 19. UI flow details

### 19.1 Student onboarding
- Landing page → student registration
- Registration submits form data and profile picture
- User receives email verification
- After verification, user logs in with wallet number and password
- Student dashboard shows wallet balance and transaction list
- Student can deposit, transfer funds, and update profile

### 19.2 Merchant onboarding
- Merchant registration includes profile picture, business name, bank details, and school code
- Merchant gets email verification
- Merchant cannot log in until approved
- After approval, merchant logs in with wallet number
- Merchant dashboard shows business name, approval status, QR code, wallet balance
- Merchant can withdraw funds, scan to charge, update profile, download QR code

### 19.3 Admin / school admin workflow
- Admin logs in via /Admin/login
- Admin can create school admins
- Admin can delete users
- Admin can view bank list and approve or manage data
- SchoolAdmin logs in via /SchoolAdmin/login
- SchoolAdmin approves merchant accounts
- SchoolAdmin can manage school user lists

### 19.4 Transaction path
- Deposit page for students only
- Transfer page for students only
- Withdrawal page for merchants only
- Scan-to-charge page for merchants only
- Transaction history page for all authorized users
